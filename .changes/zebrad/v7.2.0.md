## [Zebra 7.2.0](https://github.com/ZcashFoundation/zebra/releases/tag/v7.2.0) - 2026-11-27

### Breaking Changes

- Changed OpenTelemetry trace sampling to follow the OpenTelemetry specification. `OTEL_TRACES_SAMPLER_ARG` is now a ratio between 0.0 and 1.0, and applies only when `OTEL_TRACES_SAMPLER` is set, for example `OTEL_TRACES_SAMPLER=traceidratio` and `OTEL_TRACES_SAMPLER_ARG=0.1` for 10% of traces. If you set `OTEL_TRACES_SAMPLER_ARG` to a percentage, set these two variables instead, or set `ZEBRA_TRACING__OPENTELEMETRY_SAMPLE_PERCENT`, which still takes a percentage.

### Added

- `getblockchaininfo` and verbose `getblock` responses include `nsmValueBalance`, the Network Sustainability Mechanism (NSM) value balance from NU7, with the block's change to it in `getblock`. It is not part of `chainSupply` or `valuePools`. As [ZIP 237](https://zips.z.cash/zip-0237) defines it, the balance after the block before NU7 activation is `INITIAL_NSM_VALUE_BALANCE`. ([#12325](https://github.com/ZcashFoundation/zebra/pull/12325))
- Added static user and password authentication for the JSON-RPC server: set `rpc.rpc_user` with `rpc.rpc_password` or `rpc.rpc_password_file` to require fixed HTTP Basic credentials instead of the cookie. ([#12403](https://github.com/ZcashFoundation/zebra/pull/12403))
- Added the `network.compact_block_relay` option, off by default. Zebra nodes that both set it advertise the service bit of the draft Compact Block Relay ZIP, and announce new blocks to each other as a header and short transaction IDs, and rebuild each block from their mempools instead of downloading its transactions again. Every rebuilt block is still verified like any other block. The `zebra.net.compact_block.admitted` and `zebra.net.compact_block.rebuilt` metrics count the announcements a node kept and the blocks it rebuilt from them.
- Added the standard Prometheus process metrics, such as `process_resident_memory_bytes`, `process_open_fds`, and `process_cpu_seconds_total`, which Zebra samples every 15 seconds when the metrics endpoint is open or Sentry is active, except on Windows.
- Added a description and unit for every Zebra metric, which the Prometheus endpoint shows as `# HELP` lines, and the metric catalog in `docker/observability/metrics-catalog.json`, which lists each metric's kind, unit, description, labels, and Prometheus series names.
- Added the `commit` label to `zebrad_build_info`, and metrics that time each phase of block verification, checkpoint commits, block decoding, gossiped block downloads, block template building, the first template after a new tip, mined block announcements, and mempool cleanup, with `submitblock` outcome counts. They are exported as Prometheus histograms, so they can be aggregated across nodes.
- Added the `tracing.log_format` option. Set it to `"json"`, or set `ZEBRA_TRACING__LOG_FORMAT=json`, to write one JSON object per line, which log collectors such as Google Cloud Logging, Azure Monitor, Grafana Loki, and Datadog read without a custom parser. In JSON mode a panic is written to standard error as one JSON line, whether or not `SENTRY_DSN` is set.

### Changed

- Store and announce verified transactions without waiting for the five-second mempool queue check on idle nodes ([#11376](https://github.com/ZcashFoundation/zebra/pull/11376)).
- Lowered block and transaction verification latency by flushing proof and signature batches after 5 ms of idle input, while retaining the 100 ms maximum batch latency.
- Note commitment trees are updated faster for blocks with many shielded outputs, which speeds up block commits and checkpoint sync.
- Verify new blocks on the best chain tip faster when their transactions are already in the mempool, so Zebra commits and relays them, and answers `submitblock`, with less delay. Zebra reuses the mempool's verification of those transactions, and only checks the rules that depend on the block for them, such as expiry heights and lock times. The `zebra.consensus.block.mempool_reuse.hit` and `miss` metrics count the transactions in new blocks that Zebra takes from the mempool's verification or verifies itself, and the `timeout` and `error` metrics count the mempool lookups that time out or fail.
- Reduce cold submitblock latency by decoding large blocks in parallel.
- Batch Orchard and Ironwood commitment-tree hashes by level using checked upstream Sinsemilla evaluation ([#11846](https://github.com/ZcashFoundation/zebra/pull/11846)).
- Prepare checked Orchard tree hash tables in the background during startup without delaying RPC initialization ([#11846](https://github.com/ZcashFoundation/zebra/pull/11846)).
- Gossip newly committed blocks to peers right away, instead of waiting 7 seconds before each one.
- Decode large blocks received from peers in parallel, like submitted blocks.
- Rebuild the mining block template when the mempool verifies a new transaction, at most once a second, instead of only every 5 seconds.
- Serve a coinbase-only block template on top of a new block as soon as its proof of work is checked, without waiting for its transactions to be verified. The template is withdrawn if the block is rejected, or if it takes more than a second to verify, and miners get the previous template again.
- Commit a block that was already validated as a block proposal, like a solved `getblocktemplate` template, without validating it again. Only its proof of work and time are checked.
- Validate each new mining block template as a block proposal in the background, so a miner that submits it unchanged, apart from the nonce and solution, gets it committed without another validation.
- Reduced the work Zebra does when Sentry is enabled: it no longer builds a Sentry span for every INFO-level span, such as one per inbound peer message. Zebra doesn't send Sentry traces, so these spans were never sent.
- Stopped starting the Sentry session rotation and metrics flush threads when `SENTRY_DSN` is unset or the Sentry client is disabled.
- Changed `rpc.request.duration_seconds` and `zcash.net.peer.handshake.duration_seconds` to Prometheus histograms: the endpoint now exports `_bucket` series for them instead of `quantile` series, so they can be aggregated across nodes. The supplied dashboards and alert rules already query the `_bucket` series.
- Changed the `zcash.net.peers.missing_services` label from `remote_services`, the service bits the rejected peer sent, to `missing_service`, the required service it lacks, such as `NODE_NETWORK`. Removed the `cache` label, the peer cache file path, from `zcash.net.peers.initial` and `zcash.net.peers.cache`. The `seed` label of `zcash.net.peers.initial` now names only Zebra's default DNS seeders, and labels every other configured initial peer `custom`. Update dashboards and alerts that select on these labels.
- Zebra caches successful transparent script verifications, so an input script verified when its transaction entered the mempool is not verified again when a block mines that transaction with the same spent outputs and network upgrade. A cache hit skips only that input's script. The cache is reported by the `zebra.consensus.cache.*` metrics with the `transparent_script` verifier label ([#11939](https://github.com/ZcashFoundation/zebra/pull/11939)).
- Commit a solved `getblocktemplate` template without decoding its transactions again.
- Updated the `libz-sys` build dependency to 1.1.33, clearing RUSTSEC-2026-0544. Zebra isn't affected: zebrad only uses it at build time, through `vergen-git2`, and never calls `gzprintf`.
- Changed the metrics sent to Sentry when `SENTRY_DSN` is set: Zebra now sends every metric that the Prometheus endpoint exports, instead of a fixed list, once a minute. Counters send their increase, gauges their latest value when it changes and at least every 5 minutes, and histograms up to 20 values per set of labels as distributions. Each minute sends at most 1,500 metrics and at most 256 sets of labels per metric, and sends none while the Sentry SDK is still sending earlier data, so metrics never fill the queue they share with events, logs, and sessions. The new `zebrad.sentry.metrics.dropped.total` counter counts the values left out. Metrics also carry `chain.near_tip`, which is `true` when the node is near the chain tip.
- Added the `chain_network_upgrade` label to `zcash.chain.tip.block_delay_seconds`, the network upgrade at the block's height. Sentry still receives each value's block height as the `chain.height` attribute.
- Updated `url` to 2.5.9, clearing RUSTSEC-2026-0592. Zebra isn't affected: neither Zebra nor its dependencies call `Url::origin()` ([#12577](https://github.com/ZcashFoundation/zebra/pull/12577)).
- Changed `cargo binstall zebrad` so it no longer falls back to third-party QuickInstall builds on platforms without a release archive. `cargo binstall` does not check the Cosign signature or the build-provenance attestation of the release archive, so the install guide now says so and lists the verified manual download first.
- Added the `siphasher` dependency, which the compact block encoding uses for short transaction IDs.
- The `submitblock` RPC returns `inconclusive` for a block that is not verified and committed within 30 seconds, instead of waiting until the block is committed or dropped. Zebra keeps verifying the block, and commits and announces it if it is valid. A block whose parent never arrives used to wait for about a hundred blocks.
- Changed the mempool to accept and relay transactions that pay at least 400 zatoshis per ZIP 317 logical action, with a minimum of 800 zatoshis per transaction, down from 1,000 per logical action and 2,000 per transaction. `getstandardfee` still recommends 1,000 zatoshis per logical action to wallets.

### Fixed

- Avoid dropping compatible replacement peers at network upgrade activation when an outdated connection still occupies the same IPv4 address or IPv6 /64 connection slot ([#12109](https://github.com/ZcashFoundation/zebra/issues/12109)).
- Fixed verbose `getblock` responses reporting each whole value pool balance as the block's `valueDelta` and `valueDeltaZat` when the parent block's balances were not found, for example after a reorg during the request. These fields are now omitted in that case. ([#12325](https://github.com/ZcashFoundation/zebra/pull/12325))
- Fixed supplied Grafana panels, alert rules, and example queries that queried series Zebra doesn't export. The `ZebraHighErrorRate` alert now fires on block verification errors from `sync.block.error.count`, the errors dashboard shows signatures and shielded bundles in batches that failed verification, which the endpoint now exports at zero from startup so the first failures show in `rate()`, the observability README checks `zcash_chain_verified_block_height`, the `RPCHighLatency` alert ignores `getblocktemplate` long polls, and the `SlowHandshakes` alert fires when the p95 successful handshake takes over 2 seconds, below the 3 second handshake timeout. The RPC tracing dashboard now queries the span metrics that the supplied Jaeger configuration exports, so its panels are no longer empty, and its error panels show zero for methods with requests but no errors.
- Decode the messages a peer sends after a message that Zebra ignores, such as one with an unknown command, without waiting for the peer to send more data.
- Fixed a node that is syncing below a network upgrade banning honest peers that relay transactions for that upgrade. Without peers, the node could stop syncing just before the upgrade's activation height.
- Fixed the mempool starting on Mainnet while the node is still far behind the network chain tip. Short sync batches from a node with few useful peers no longer turn it on, because the best tip must also be at most 125 minutes old, the same limit `getblocktemplate` applies. Test networks are unchanged.
- Zebra no longer stalls its initial sync on pruned Zakura peers (Zakura 1.8.8 and later) that advertise `NODE_NETWORK` with `NODE_PRUNED`. It doesn't use them as new outbound peers while syncing, or as a source of historic blocks. Since mid-November, these peers made Mainnet syncs from genesis about 50% slower. Zebra also asks other peers up to two more times before dropping a chain tip that no peer answered, instead of restarting the sync.
- Fixed OpenTelemetry tracing, which exported either every span or none from each node, because the process-long global span was the root of every trace. Each peer connection attempt, handshake, peer request, checkpoint verification, and RPC or gRPC request now starts its own trace, with any inbound or mempool request it makes inside it, and only WARN and ERROR log events are attached to spans. Long-running spans, such as the syncer and the peer crawler, are no longer exported.
- Fixed Docker containers failing to start when run as a non-root user (for example with `--user 10001:10001`), because the entrypoint aborted after it could not take ownership of the cache directory. The entrypoint now prepares directories only when it is running as root, so a non-root start relies on the directory's existing permissions. ([#12590](https://github.com/ZcashFoundation/zebra/pull/12590))
