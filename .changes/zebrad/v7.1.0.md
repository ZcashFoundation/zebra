## [Zebra 7.1.0](https://github.com/ZcashFoundation/zebra/releases/tag/v7.1.0) - 2026-11-16

This release fixes several security issues that let peers or RPC clients exhaust a node's memory or stall its initial sync. All node operators should upgrade. It is supported until around 10 December 2026; upgrade to the next release before then.

### Breaking Changes

- Remove the experimental `elasticsearch` feature, which exported finalized blocks to Elasticsearch and slowed down syncing. A config that still has `elasticsearch_url`, `elasticsearch_username`, or `elasticsearch_password` in the `[state]` section now fails to load: delete those fields.

### Added

- Added stack traces to Sentry error events, with Zebra's frames marked in-app, so Sentry can show suspect commits. Sentry now groups logged errors by stack trace, so existing issues may reappear as new ones ([#11855](https://github.com/ZcashFoundation/zebra/pull/11855)).
- Added the `zcash.chain.tip.block_delay_seconds` histogram, which measures how long after its header time each new tip block is accepted, and sent it to Sentry as a distribution, with the block's height, when `SENTRY_DSN` is set. Metrics sent to Sentry also carry the network upgrade at the tip and the process uptime.
- Added sync stall diagnosis. Sync restarts now log why they happened, block download and verify errors include a `kind`, and the "chain updates have stalled" warning includes the latest restart reason and the age of the oldest in-flight block. The new `sync.restart.count`, `sync.block.error.count`, and `sync.downloads.oldest_age_seconds` metrics are exported to Prometheus, and sent to Sentry once a minute when Sentry is enabled.
- Added the verified block counts, the mempool size, and the database disk size to the metrics sent to Sentry once a minute when `SENTRY_DSN` is set, to help compare nodes.
- Added memory metrics: the process's memory use and its share of available memory, the size of the non-finalized state, forks evicted, and the non-finalized backup restore. Official release builds send them to Sentry once a minute when `SENTRY_DSN` is set.

### Changed

- Disabled Nagle's algorithm (`TCP_NODELAY`) on peer connections, like zcashd does. This removes delays of 40ms or more when Zebra sends several small messages in a row, for example when it relays mempool transactions to zcashd peers.
- RPC requests without valid cookie credentials now get an HTTP 401 response with a JSON-RPC error body instead of an empty reply ([#9190](https://github.com/ZcashFoundation/zebra/issues/9190)).
- Block queue and commit spans no longer include whole verified-block payloads; compact height and hash context remains.
- Routine state-service spans now use DEBUG, and per-input, per-transaction, and chain-tip getter spans use TRACE. INFO events and their fields are unchanged.
- A node with no outbound peers and no peer addresses to try now resolves its DNS seeders, reloads its configured and cached peers, and retries peers that failed, at most once every 5 minutes, instead of staying without peers until it is restarted. It logs a warning each time ([#11807](https://github.com/ZcashFoundation/zebra/pull/11807)).
- Zebra now starts with its cached peers when DNS resolution of the initial peers fails, instead of waiting for DNS to succeed ([#11807](https://github.com/ZcashFoundation/zebra/pull/11807)).
- The mempool no longer scores V4 transactions that fail transparent script verification within the branch ID grace period around a network upgrade activation, because they may have been signed for the adjacent upgrade. Outside that window, script failures keep their misbehavior score.
- Bound metric labels: `mempool.failed.verify.tasks.total` uses error kinds for `reason` (retaining `timeout`), `zebra.net.in.errors` uses error kinds for `error`, and handshake protocol-version labels use known versions or `other`. Update custom selectors that match full error messages or unknown protocol versions.
- Stop sending requests to a peer that was banned, or made obsolete by a network upgrade, after Zebra selected it, including while waiting for its connection to become writable.
- With `ephemeral = true`, `zebrad` no longer leaves empty directories in the temporary directory each time it starts.
- Read-write nodes now report incomplete stored block bodies through block RPC and peer requests instead of serving empty or partial blocks.
- Updated the `pulldown-cmark` build dependency to 0.13.6, clearing RUSTSEC-2026-0414 and RUSTSEC-2026-0433. Zebra isn't affected; it only runs the crate at build time, on the doc comments of its own protobuf files.
- `zebrad` now stops at config load when a configured network upgrade height has no consensus branch ID in this build, instead of panicking at that upgrade's activation block. This only affects custom Testnet and Regtest configs ([#11482](https://github.com/ZcashFoundation/zebra/issues/11482)).
- Updated the `libz-sys` build dependency to 1.1.31, clearing RUSTSEC-2026-0418. Zebra isn't affected: the leak needs `cc` 1.6.0 or later, and Zebra's lockfile uses `cc` 1.2.61.
- Changed the log for a sync round that ends with an error without advancing the chain tip from INFO to WARN, so it reaches Sentry Logs and WARN-level alerts. The separate INFO `temporary error obtaining tips` and `temporary error extending tips` lines are gone, because the warning includes their error.
- Zebra no longer gossips peer addresses as full nodes (`NODE_NETWORK`) when it never learned their services, and gossips an inbound peer's listener address with the services that peer advertised.
- Unsolicited transactions from peers no longer interrupt block and transaction downloads, and Zebra only treats a peer as missing a block or transaction when the peer says so. A request for an exact transaction also matches its authorizing data, so a peer that serves a differently signed copy is treated as not having it.
- Checkpoint sync commits blocks with transparent outputs faster.
- Reduce CPU work when updating mempool rejection metrics.
- Reduce build dependencies without changing node behavior.
- This release is supported for 24 days instead of 8 weeks, so it stops around 10 December 2026, near block 3,607,648, and warns from about 3 December. Upgrade to the next release before then.

### Fixed

- Misbehavior score increments are no longer lost while earlier scores are being applied under load ([#10601](https://github.com/ZcashFoundation/zebra/issues/10601)).
- Failed client connections to the tracing filter endpoint (built with the `filter-reload` feature) are now logged as warnings instead of errors, so they no longer create Sentry issues when Sentry is enabled.
- Fixed the startup panic when the state database cannot be opened: it now shows the underlying error, and only blames another running zebrad process when the database lock is actually held. Other I/O errors, such as an unmounted, unwritable, or full cache directory, get their own message.
- Fixed `zebrad tip-height` and `zebrad copy-state` leaving a `zebra-secondary_state-*` directory in the system temporary directory each time they ran. These directories are now removed on exit. Existing ones can be deleted safely when no zebrad command is running.
- Improved how the non-finalized state tracks blocks from chain forks it no longer keeps.

### Security

- Keep a sync round going when a peer's reply to a sync discovery request includes blocks Zebra already has, and skip downloading those blocks ([GHSA-vw2c-5w35-x5q6](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-vw2c-5w35-x5q6)). Thanks to @AnticsDecoded for reporting the issue.
- Check mempool transactions for unknown anchors and spent nullifiers before verifying their proofs, so transactions rejected by those checks no longer add work to the proof batches shared with block verification ([GHSA-2wx4-g5cf-32pf](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-2wx4-g5cf-32pf)). Thanks to @Nathanbyarugaba and @SphereDonout for reporting these issues.
- Stopped transparent address balance requests, including `getaddressbalance` RPCs and lightwalletd `GetTaddressBalance` calls, from copying the whole non-finalized chain. A recent block with many transparent outputs made each copy large, so concurrent balance requests could run the node out of memory ([GHSA-hj54-2mfv-4xg8](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-hj54-2mfv-4xg8)). Thanks to @saxenism for reporting the issue.
- Stopped `getaddressutxos` and `getaddresstxids` requests from copying every recent UTXO and transaction of the requested addresses on each request ([GHSA-hj54-2mfv-4xg8](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-hj54-2mfv-4xg8)).
- Update `ctutils` to 0.4.5 to fix RUSTSEC-2026-0385, non-constant-time mask generation and `u128` comparisons. Zebra holds no keys and uses the affected hashing and signature code on public data.
- Update tokio to 1.54.1 to fix RUSTSEC-2026-0386, safe `AsyncFd` constructors that violate I/O safety. Zebra doesn't use `AsyncFd`.
- The health endpoint serves one request per connection, closes connections that don't send their request headers within 5 seconds, and keeps at most 32 connections open, so slow or idle clients can't use up its connections.
- Limit the memory a peer's block request can use: Zebra keeps at most 16 distinct block hashes from it before handling the request.
- Prevent forged queued blocks from causing honest replacement peers to be penalized ([GHSA-7jvw-68q7-xfh4](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-7jvw-68q7-xfh4)). Thanks to @x15-eth for reporting the issue.
- Release completed block downloads between sync rounds, and retry missing ancestors a limited number of times, including in rounds with no new tips or only one advertised hash.
- Bound block downloads by the remaining sync lookahead capacity, reserving space for retries and the final checkpoint. Block hashes from different peers are interleaved, so one peer's response can't fill the download batch.
- Keep unrelated block verification running when a peer serves an invalid block or a download fails, and retry blocks whose bodies fail validation. A sync round where the chain tip doesn't advance for 8 minutes now backs off without cancelling downloads. It counts under the `sync_step_timeout` reason of `sync.restart.count` and logs `no chain progress before the sync deadline` at INFO, not the WARN for a failed sync round. Tip progress during a pending request restarts the 8 minutes.
- Time out stalled block-verifier readiness so downloaded blocks cannot remain pending indefinitely between sync rounds.
- Ban peers that serve a requested block whose transactions don't match its header, such as a block with a rewritten coinbase height, and request the block again from another peer, so a peer can't stall initial sync by making Zebra drop a block it still needs ([GHSA-g9rc-89v4-hhvf](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-g9rc-89v4-hhvf), [GHSA-hvw5-x88g-2q8w](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-hvw5-x88g-2q8w)). Thanks to @x15-eth and @SphereDonout for reporting these issues.
- Reject mempool transactions with more than 4,000 signature operations before verifying their scripts. Previously, a peer could keep the verification thread pool busy with transactions that Zebra verified in full before rejecting them as non-standard ([GHSA-423j-2vj4-j5x4](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-423j-2vj4-j5x4)). Thanks to @janneh2000 for reporting the issue.
- Limit the memory of blocks waiting for checkpoint verification and of blocks waiting for their parent blocks, including blocks kept alive after their requests were cancelled or their commits failed. The syncer requests a block dropped from a full queue again without cancelling other downloads, and restarts the round if those downloads run out of retries. The `sync.block.error.count` metric counts these errors with the `queue_full` kind ([GHSA-8qxv-5f2c-452c](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-8qxv-5f2c-452c)). Thanks to @Maakai123, @DanielDerefaka, and @SphereDonout for reporting the issue.
- Fix an initial sync halt where a peer could send forged blocks during the switch from checkpoint sync to full validation, so later blocks were never committed. Zebra now rejects those blocks and bans the peer that sent them ([GHSA-m44m-9r8r-r64j](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-m44m-9r8r-r64j)). Thanks to @unusualbyte for reporting the issue.
- Limit the combined size of the non-finalized chain indexes to about 5–7 GB, so a long run of blocks filled with transparent outputs can't exhaust the node's memory. 16 GB of RAM is recommended. Past the limit, which ordinary Mainnet blocks don't reach, Zebra drops the lowest-work forks, and if the chains are still too large, it finalizes the best chain's oldest blocks early, keeping at least 100. While it does, Zebra can't follow a chain reorganization deeper than the blocks it kept. Test networks have a lower limit ([GHSA-j8gf-c4rj-6jv5](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-j8gf-c4rj-6jv5)).
- Fix a denial of service where blocks with many transparent outputs made every non-finalized fork, and every finalized block, copy the created-output and address indexes of the whole non-finalized window, so a node ran out of memory and was killed again on every restart. Chain forks now share each block's outputs and address changes instead of copying them ([GHSA-j8gf-c4rj-6jv5](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-j8gf-c4rj-6jv5)). Thanks to Foundry Digital for reporting the issue.
- Chain forks in the non-finalized state share their transaction, spend, and nullifier indexes instead of copying them, so blocks with many transactions or spends no longer multiply memory use by the number of forks ([GHSA-j8gf-c4rj-6jv5](https://github.com/ZcashFoundation/zebra/security/advisories/GHSA-j8gf-c4rj-6jv5)).
- Reject mempool transactions with non-standard outputs, such as dust or oversized `OP_RETURN` data, before verifying their scripts and proofs.
